# CampusRAG 중간발표 대본

저학년의 반란 · 2026.10.19 · 12장 · 목표 10분

각 시간은 발표와 슬라이드 전환을 포함한 권장 배분입니다. 실제 소요 시간은 리허설로 조정하세요. 질의응답은 10분에 포함하지 않습니다.

## 01. CampusRAG

**0:00–0:25 / 25초**

> 프로젝트명과 팀명을 소개한 뒤, 현재 성과와 남은 검증을 설명한다고 예고한다.

안녕하세요. 저희는 저학년의 반란 팀입니다. 한성대학교의 공식 공지와 학사 정보를 질문으로 찾아보는 웹 챗봇, CampusRAG의 중간 진행 상황을 발표하겠습니다. 지금까지는 질문을 입력하고, 관련 자료를 검색해 답변과 원문 출처를 보여주는 기본 흐름을 구현했습니다. 오늘은 서비스가 해결하려는 문제, 구현 결과와 데이터 개선, 그리고 최종 발표까지 남은 과제를 순서대로 말씀드리겠습니다.

## 02. 학내 정보 탐색의 어려움

**0:25–1:10 / 45초**

> 공지 제목에서 실제 신청 조건까지 확인하는 과정을 손으로 짚는다.

학생이 학교 정보를 찾을 때는 단순히 공지 제목 하나를 찾는 것으로 끝나지 않습니다. 예를 들어 장학금 신청을 알아보려면 어느 게시판에 있는지 찾고, 본문이나 첨부파일을 열어 기간과 대상 조건을 확인해야 합니다. 비슷한 제목의 예전 공지까지 함께 보이면 어느 학기 자료인지도 구분해야 합니다. 저희가 해결하려는 문제는 이 탐색 과정의 번거로움입니다. 학생이 평소 쓰는 문장으로 질문하면 관련 공식 자료를 모아 답하고, 확인할 원문까지 연결하는 것을 목표로 잡았습니다. 탐색 시간이 얼마나 줄어드는지는 앞으로 사용자 테스트에서 측정할 예정입니다.

## 03. 현재 개발 범위

**1:10–1:55 / 45초**

> 포함 범위를 먼저 설명하고, 범위를 정리한 이유를 덧붙인다.

중간 단계에서는 개발 범위를 공식 정보 질의응답에 집중했습니다. 로그인 없이 질문하고, 근거를 바탕으로 만든 답변과 출처 카드를 확인하는 흐름입니다. 수강, 장학, 휴학과 복학, 졸업, 학교생활 정보를 대상으로 하며, 자료가 부족한 경우의 안내도 포함합니다. 초기 계획에 있던 회원가입, 개인 일정 등록, 캘린더와 마감 알림은 현재 범위에서 제외하고 관련 코드를 별도로 보관했습니다. 질문의 정확성과 출처 확인을 먼저 완성하기 위한 결정입니다. 또 화면에 이전 대화가 남더라도 서버는 현재 질문만 처리합니다. 앞선 대화 내용을 기억하는 기능은 후속 확장 과제입니다.

## 04. 사용자 화면과 이용 흐름

**1:55–2:55 / 60초**

> 왼쪽 실제 초기 화면을 가리킨 뒤, 오른쪽의 질문·답변·출처 단계를 따라 설명한다.

왼쪽은 현재 웹 빌드를 로컬에서 연 초기 화면입니다. 학생은 예시 질문을 선택하거나 입력창에 직접 질문할 수 있습니다. 질문을 보내면 화면에 대기 상태가 나타나고, 응답을 받은 뒤 답변과 참고 공식 공지를 표시합니다. 출처에는 제목과 분류 같은 정보가 있고, 원문 바로가기로 학교 페이지를 확인할 수 있습니다. 여기서 중요한 점은 답변과 원문 확인을 한 흐름으로 연결했다는 것입니다. 화면은 모바일 중심으로 구성했고, 중복 전송 방지와 대화 초기화, 프로젝트 안내 화면도 구현했습니다. 오늘 화면은 초기 상태를 보여주는 자료이며, 실제 모델의 정답 사례를 시연한 화면은 아닙니다. 최종 시연에서는 고정한 질문을 실제 모델로 실행하고 출처까지 대조하겠습니다.

## 05. 시스템 구조

**2:55–3:55 / 60초**

> 위쪽 질의 처리 흐름과 아래쪽 지식 준비 흐름을 구분해 짚는다.

CampusRAG는 검색한 자료를 생성 모델에 함께 제공하는 RAG 구조를 사용합니다. 먼저 React 웹이 현재 질문을 FastAPI로 보냅니다. 서버는 입력을 확인하고 한국어 임베딩과 Chroma를 이용해 관련 문서 조각을 찾습니다. 이후 선택한 근거로 생성 모델이 답변을 만들고, 답변과 출처를 웹에 돌려줍니다. 생성 모델은 설정에 따라 선택할 수 있으며, 검색용 임베딩은 생성 모델과 별도로 서버에서 실행합니다. 아래는 지식을 준비하는 과정입니다. 공식 공지와 안내를 수집하고, 이미지와 첨부파일의 텍스트를 추출한 뒤 통합 자료와 검색 색인을 만듭니다. 따라서 웹 화면이 실행되는 것과 지식이 최신 상태인 것은 각각 확인해야 합니다. 저희는 두 흐름을 나눠 구현하고 검증하고 있습니다.

## 06. 지식 데이터 개선 결과

**3:55–4:55 / 60초**

> 로컬 확장본이라는 조건을 먼저 말하고, 문서·청크·제목 전용 문서를 차례로 설명한다.

데이터 개선은 현재까지의 주요 성과입니다. 10월 9일 생성한 로컬 확장본은 1,485문서와 6,886청크입니다. 청크는 검색에 사용하는 문서 조각을 뜻합니다. 기존 기본 자료의 1,366문서와 3,447청크에서 범위를 넓혔고, 제목만 확보했던 문서는 202건에서 3건으로 줄였습니다. 구성은 공지 1,105건, 상시 안내 144건, FAQ 179건, 서식 57건입니다. 이미지와 첨부 본문을 보강하면서 제목만으로 추측하던 상황을 줄였다는 점에 의미가 있습니다. 다만 텍스트가 존재한다고 내용이 모두 정확하게 추출됐다는 뜻은 아닙니다. OCR 날짜와 마감 시각은 원문 대조가 필요합니다. 또한 이 수치는 로컬 확장 결과이며, 원격 저장소의 기본 자료나 운영 서버에 같은 버전이 적용됐다고 단정하지 않습니다.

## 07. 근거와 예외 처리

**4:55–5:50 / 55초**

> 정상 답변과 유보·오류를 서로 다른 결과로 설명한다.

답변 품질을 위해서는 관련 자료를 찾는 것뿐 아니라, 답하기 어려운 상황을 구분하는 것도 필요합니다. 현재는 근거를 확보한 경우 답변과 출처를 반환하고, 관련 자료가 없으면 근거 부족을 안내합니다. 제목만 확보한 공지라면 자세한 조건을 만들어내지 않고 원문 확인을 안내합니다. 생성 API나 네트워크에 문제가 생기면 이를 오류로 표시합니다. 이 구분 덕분에 사용자는 답변을 받지 못한 이유를 알 수 있습니다. 질문 길이는 서버에서 1자부터 500자까지 검증하고, 화면에서는 공백 입력과 처리 중 재전송을 막습니다. 다만 날짜나 대상 조건이 다른 공지와 섞이는 문제는 실제 답변으로 추가 확인해야 합니다. 예외 처리의 구현과 사실 정확도 평가는 별도로 보고 있습니다.

## 08. 검증 결과와 해석

**5:50–6:45 / 55초**

> 검사 날짜와 대상을 먼저 설명하고, 정답률로 해석하지 않음을 분명히 한다.

검증 결과는 날짜와 대상을 구분해 정리했습니다. 10월 9일 로컬 확장 작업에서는 데이터와 색인의 엄격 동기화 검사, 대표 검색 여섯 건, 관련 회귀 검사 163건을 통과한 기록이 있습니다. 이후 10월 18일 설계 문서 작업 때 실행한 별도 선별 검사 58건에서는 57건이 통과하고 한 건이 실패했습니다. 실패는 모델을 미리 불러오지 않은 상태에서 헬스 API의 문서 수가 0으로 표시되는데, 테스트는 1 이상을 기대한 사례입니다. 생존 확인과 검색 준비 상태의 기준을 맞추는 작업이 남아 있습니다. 두 검사는 대상이 다르므로 통과 개수를 직접 비교하지 않습니다. 특히 이 숫자를 챗봇 답변의 정답률로 제시하지 않고, 실제 모델의 정확도와 응답시간은 별도 평가하겠습니다.

## 09. 단계별 진행 상황

**6:45–7:25 / 40초**

> 완료·구현·검증 예정의 의미를 구별하고, 설계 산출물로 연결한다.

현재 진행 상황을 단계별로 보면, 챗봇 중심으로 요구사항을 정리했고 웹과 API, 검색·생성의 기본 흐름을 구현했습니다. 로컬 지식 확장과 검색 검증도 진행했습니다. 10월 18일에는 기술 요구사항 정의서, 프로그램 목록, 화면 설계서와 형상관리표를 정리해 기능과 코드, 시험 항목의 연결을 문서화했습니다. 반면 실제 모델의 종합 답변 평가와 최신 지식의 운영 적용, 학생 사용자 테스트는 남아 있습니다. 그래서 임의의 전체 완료율 대신, 무엇을 구현했고 어떤 검증이 필요한지를 단계별 상태로 표시했습니다.

## 10. 남은 문제와 개선 방향

**7:25–8:20 / 55초**

> 각 문제를 해결 작업과 연결하고, 실제 서버 적용은 미확인이라고 설명한다.

남은 과제는 크게 세 부분입니다. 첫째는 답변 품질입니다. 학기나 공지별 신청 기간, 대상과 제외 조건이 섞이지 않는지 실제 모델 답변을 원문과 비교해야 합니다. 실패 질문은 같은 조건에서 수정 전후를 비교하겠습니다. 둘째는 최신성입니다. 원본을 수집하는 작업과 운영 검색 색인을 교체하는 작업은 다르기 때문에, 검증한 자료 묶음을 실제 서버에 반영하고 버전을 확인해야 합니다. 셋째는 사용성과 운영 안정성입니다. 500자 제한의 사전 안내, 첫 응답과 동시 요청, 오류 후 재시도를 점검해야 합니다. 현재 운영 주소에 최신 확장본이 반영됐는지와 매일 갱신하는 예약 작업의 설치 여부는 아직 확인하지 못했습니다. 최종 단계에서 이 부분을 실제 실행 기록으로 확인하겠습니다.

## 11. 최종 평가 계획

**8:20–9:15 / 55초**

> 숫자 옆의 ‘목표’를 강조하고, 오류·유보를 따로 기록한다고 설명한다.

최종 평가에서는 학사, 장학, 졸업과 휴복학 등 대표 질문을 30개 이상 고정하겠습니다. 질문마다 사용한 자료 버전과 모델, 답변, 출처와 판정을 함께 저장합니다. 검색이 필요한 근거를 찾았는지와 생성 답변이 그 근거를 정확하게 전달했는지를 구분해 보겠습니다. 목표는 핵심 사실을 근거가 지지하는 답변 90퍼센트 이상입니다. 근거 부족에 대한 적절한 유보와 API 오류도 별도로 기록하겠습니다. 사용자 평가는 학생 10명 이상이 질문부터 원문 확인까지 수행하게 하고, 성공 여부와 시간, 혼동한 부분을 수집합니다. 만족도 목표는 5점 만점에 4점 이상입니다. 화면에 적힌 수치는 모두 앞으로 확인할 목표이며, 현재 달성한 실적으로 제시하는 값은 아닙니다.

## 12. 최종 발표까지의 실행 순서

**9:15–10:00 / 45초**

> 상대적 실행 순서임을 설명하고, 마지막 핵심 문장 뒤 잠깐 멈춘다.

최종 발표까지는 먼저 최신 자료와 대표 질문을 고정하고, 실제 모델을 평가해 날짜와 대상 조건의 오류부터 개선하겠습니다. 다음으로 검증한 지식 버전을 운영에 적용하고 재시작과 복구, 정기 갱신을 확인하겠습니다. 그 뒤 학생 사용자 테스트에서 발견한 문제를 반영하고, 같은 질문과 출처를 이용해 최종 시연을 준비하겠습니다. 구체적인 담당자와 제출일은 팀 일정에 맞춰 확정할 예정입니다. 현재까지 저희는 공식 정보를 검색하고 답변과 출처를 제공하는 기본 흐름과 확장된 로컬 지식 기반을 마련했습니다. 남은 기간에는 실제 답변의 정확성과 운영 반영을 증거로 확인하는 데 집중하겠습니다. 이상으로 중간발표를 마치겠습니다. 감사합니다.

## 리허설과 예상 질문

목표 10분, 권장 범위 9분 30초~10분 30초. 실제 모델을 기다리는 실시간 시연과 질의응답은 별도입니다.

### 기존 검색이나 일반 챗봇과 무엇이 다른가요?

한성대학교 공개 공식 자료를 검색 대상으로 삼고, 검색 근거에 기반한 답변과 원문 링크를 같은 화면에서 제공합니다. 실제 탐색시간 개선은 사용자 테스트로 측정할 예정입니다.

### 정확도가 90%인가요?

90%는 최종 평가 목표입니다. 현재 종합 정확도는 미확정입니다. 회귀 검사 통과와 검색 사례 통과를 생성 답변의 정답률로 환산하지 않습니다.

### 운영 서버에도 6,886청크가 적용됐나요?
