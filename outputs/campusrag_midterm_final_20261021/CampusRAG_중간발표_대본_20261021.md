## 02 프로젝트 소개

0:20–1:05 · 45초

**진행 메모** 학생의 질문에서 공식 원문 확인까지 이어지는 흐름을 짚는다.

학교 정보를 찾다 보면 게시판을 옮겨 다니거나 첨부파일까지 열어야 합니다. 장학금 공지 하나도 신청 기간과 대상, 제출 방법을 각각 확인해야 하고, 비슷한 제목의 예전 공지와 구분해야 합니다.

CampusRAG는 이 탐색 과정을 줄이기 위한 프로젝트입니다. 학생이 평소 쓰는 문장으로 질문하면 한성대학교 공개 공식 자료를 검색하고, 관련 내용을 정리해 답합니다. 답변 아래에는 출처를 함께 보여줘 학생이 원문을 확인할 수 있게 했습니다. 현재 개발 범위는 학사와 학교생활 정보의 질의응답이며, 실제 탐색 시간의 개선 정도는 사용자 테스트에서 확인할 계획입니다.

## 03 구현 기능

1:05–2:00 · 55초

**진행 메모** 질문 입력, 답변, 출처 카드를 순서대로 가리킨다. 설치형 앱이라고 소개하지 않는다.

현재 구현한 이용 흐름은 질문 입력, 답변 확인, 원문 확인입니다. 로그인 없이 질문할 수 있고, 예시 질문을 선택하거나 직접 입력할 수 있습니다. 요청 중에는 대기 상태를 보여주고 중복 전송을 막습니다. 답변과 함께 공식 자료의 제목과 링크를 표시하며, 관련 근거를 찾지 못하면 자료가 부족하다고 안내합니다.

화면은 휴대전화에서도 사용할 수 있도록 구성했습니다. 다만 브라우저 이용과 PWA 설치 검증은 구분하고 있습니다. 오늘은 확인된 웹 기능을 시연합니다. 또 화면에 이전 대화가 보이더라도 서버는 현재 질문 한 건을 처리합니다. 앞선 질문을 기억하는 기능은 앞으로 확장할 과제입니다. 로그인이나 개인 일정 기능보다는 검색과 답변의 품질에 먼저 집중했습니다.

## 04 개발 과정의 변화

2:00–3:10 · 70초

**진행 메모** 연표를 왼쪽부터 짚는다. Cloudtype 중지 원인을 메모리 부족으로 단정하지 않는다.

개발 과정에서는 모델과 배포 환경을 여러 차례 점검했습니다. 먼저 9월 14일에는 로컬 Qwen 모델을 평가했고, 15일에는 Gemini를 실제로 호출해 생성 동작을 확인했습니다. 이후 16일부터 Cloudtype 배포를 위한 의존성과 초기 로딩 처리를 수정했습니다.

9월 말 조사에서는 Cloudtype 무료 환경의 메모리 제약과 서비스 중지 상태를 확인했습니다. 이후에도 의존성, 화면 누락, 응답 시간 초과 문제를 수정했습니다. 다만 서비스가 중지된 원인을 메모리 부족 하나로 확정할 근거는 없습니다.

10월 9일에는 홈서버에서 Gemini로 실행한 기록이 있고, 10일부터는 로컬 Qwen 실행 기록이 이어집니다. 현재는 홈서버 GPU를 사용해 답변을 생성합니다. 이 과정에서 화면이 열리는지, 검색이 준비됐는지, 답변이 실제로 생성되는지를 따로 확인해야 한다는 점을 배웠습니다. 현재 발표도 코드에 적힌 설정과 실제 운영 상태를 대조해 구성했습니다.

## 05 현재 시스템 구조

3:10–4:30 · 80초

**진행 메모** 위쪽 질문 처리 경로를 먼저 설명한 뒤 아래쪽 자료 갱신 경로를 설명한다.

현재 시스템은 검색한 자료를 생성 모델에 함께 전달하는 RAG 구조입니다. 학생의 질문은 React 웹에서 FastAPI 서버로 전달됩니다. 서버는 한국어 임베딩 모델로 질문을 표현하고, Chroma에서 관련 문서 조각을 검색합니다. 임베딩은 질문과 자료의 관련성을 비교하기 위한 모델이며, 답변을 쓰는 생성 모델과는 역할이 다릅니다.

검색 결과를 근거로 로컬 Qwen 모델이 답변을 만들고, 서버는 답변과 출처를 웹으로 돌려줍니다. 현재 생성 연산은 홈서버의 RTX 3060 Laptop GPU에서 CUDA로 처리합니다. 사용자는 HTTPS 주소로 접속하며, Cloudflare Tunnel이 요청을 홈서버에 연결합니다.

아래쪽은 자료를 준비하는 과정입니다. 학교 공식 공지와 안내를 모으고 이미지나 첨부파일의 글을 추출한 뒤 검색용 색인을 만듭니다. 매일 갱신 작업이 자료를 검증하고 운영 스냅샷을 적용하도록 구성했습니다. 따라서 생성 모델의 실행 상태와 자료의 갱신 상태를 함께 점검합니다. 이제 이 흐름이 웹에서 어떻게 보이는지 시연하겠습니다.

## 07 개발 완료와 개선 과제

7:30–9:10 · 100초

**진행 메모** 완료된 기능을 먼저 짚고, 실패 관찰과 다음 작업을 연결한다. 정확도 비율은 말하지 않는다.

현재까지 웹과 API, 검색과 로컬 생성의 연결, 답변과 출처 표시, 홈서버 운영 경로를 구현했습니다. 공식 자료를 갱신하고 검증한 검색 자료를 적용하는 경로도 확인했습니다. 방금 보신 FAQ와 행사 질문은 실제 답변을 원문과 비교한 사례입니다. 다만 이 사례만으로 전체 정확도를 말할 수는 없습니다.

개선 과제는 실제 실패에서 정했습니다. 먼저 표와 이미지의 내용 보존입니다. 장학 공지 포스터의 접수 기간은 10월 16일부터 11월 16일까지였지만, 답변은 시작일인 10월 16일을 마감일로 잘못 말했습니다. 자료 추출 단계에서 표와 날짜 관계를 보존하고, 생성된 핵심 날짜를 근거와 다시 대조해야 합니다.

다음은 시점 판단입니다. 오늘 날짜와 해당 학기, 이미 끝난 기간을 구분해 과거 공지를 현재 모집처럼 안내하지 않도록 보완할 계획입니다. 마지막은 질문 표현에 따른 검색 차이입니다. 인사말을 붙인 도서관 운영시간 질문에서 관련 자료를 찾지 못한 사례가 있어, 인사말 정리와 도서관 명칭의 동의어 처리를 검증하려 합니다.

같은 질문과 원문을 고정해 수정 전후를 비교하고, 검색 실패와 생성 오류를 나눠 기록하겠습니다. 이후 학생 사용자 테스트로 질문부터 원문 확인까지 막히는 지점을 점검하겠습니다.

## 08 역할 분담

9:10–10:00 · 50초

**진행 메모** 이름 칸은 네 칸 모두 비워 둔다. PWA는 담당 역할, 네 번째 역할은 향후 담당안으로 설명한다.

역할 분담은 화면과 같이 정리했습니다. 개발 총괄은 설계와 핵심 기능 개발, 통합과 배포를 담당합니다. PWA 구현은 별도 역할로 두었으며, 현재 운영본에서 설치 동작까지 확인한 상태는 아닙니다. 데이터 수집과 정리는 공식 자료의 범위와 내용을 보강하는 역할입니다.

기능 테스트와 사용성 점검은 향후 담당안으로 두고, 실제 수행 기록을 남기면서 진행할 계획입니다. 남은 기간에는 날짜와 조건의 오류, 질문 표현에 따른 검색 실패를 우선 줄이고, 같은 기준으로 결과를 다시 확인하겠습니다. 이상으로 CampusRAG 중간발표를 마치겠습니다. 감사합니다.

## 발표 종료 후 예상 질문

아래 문답과 수치는 발표 본문 10분에 포함하지 않습니다. 운영 수치는 2026년 10월 21일 확인 기록 기준입니다.

### 1 RAG를 사용한 이유는 무엇인가요

한성대학교 공식 자료를 검색 근거로 제공하고 답변과 원문 링크를 함께 보여주기 위해 사용했습니다. 모델이 근거를 잘못 요약할 수 있으므로 검색 성공만으로 정답을 보장하지는 않습니다.

### 2 현재 데이터 규모와 최신성은 어느 정도인가요

2026년 10월 21일 운영 확인 기준 원문 1,529문서와 검색용 7,202청크입니다. 청크는 문서를 나눈 검색 단위입니다. 안내 145건, FAQ 179건, 서식 57건, 공지 1,148건을 포함합니다. 확인된 최신 공지 등록일은 10월 19일이며, 학교의 모든 공지를 빠짐없이 포함했다는 뜻은 아닙니다.

### 3 자료는 자동으로 갱신되나요

매일 오전 6시 KST에 수집과 검증 후 운영 스냅샷을 적용하는 작업이 설치되어 있습니다. 10월 20일 실행은 성공했고 대표 검색 4건 중 4건을 통과한 기록이 있습니다. 예약 작업 설치와 매 실행 성공은 구분해야 하며, 발표 전에는 최근 실행 상태를 다시 확인합니다.

### 4 응답 시간과 정확도는 어느 정도인가요

10월 21일 공개 HTTPS 왕복 측정에서 FAQ는 2.711초와 반복 2.691초, 행사 질문은 3.555초였습니다. 모델을 이미 불러온 뒤의 개별 사례이며, 첫 로딩이나 동시 요청 성능은 측정하지 않았습니다. 현재 종합 정확도는 미확정입니다. 과거 평가나 코드 검사 통과율을 현재 답변 정확도로 환산하지 않습니다.

### 5 자료를 찾았는데도 틀리는 이유는 무엇인가요

이미지 OCR이나 표 평문화 과정에서 날짜와 조건의 관계가 깨질 수 있고, 생성 모델이 불완전한 근거를 잘못 요약할 수 있습니다. 실제 장학 공지의 접수 기간 10월 16일~11월 16일을 답변이 10월 16일 마감으로 잘못 생성했습니다. 원문 추출 품질과 생성 결과를 각각 검증할 계획입니다.

### 6 근거가 없거나 요청이 실패하면 어떻게 처리하나요

관련 자료를 찾지 못하면 근거 부족을 안내하고, 제목만 있는 공지는 자세한 조건을 추측하지 않도록 처리합니다. 생성이나 네트워크 오류는 오류 상태로 반환합니다. HTTP 200이나 success 상태는 처리가 끝났다는 뜻이며 내용이 정답이라는 판정은 아닙니다. 질문 길이는 서버에서 1~500자로 검증합니다.

### 7 현재 모델과 서버 사양은 무엇인가요

생성 모델은 Qwen/Qwen2.5-1.5B-Instruct이며 한국어 검색 임베딩은 jhgan/ko-sroberta-multitask입니다. Windows 홈서버의 Docker 환경에서 실행하고, NVIDIA RTX 3060 Laptop GPU의 6GB VRAM을 사용합니다. PyTorch CUDA 활성화와 실제 로컬 생성 응답을 확인했습니다. GPU 메모리 관찰값은 프로세스 전체 사용량이므로 모델 단독 사용량으로 제시하지 않습니다.

### 8 Cloudtype에서 홈서버로 바꾼 이유는 무엇인가요

Cloudtype에서는 제한된 메모리 환경과 배포, 초기 로딩, 응답 시간 초과 문제를 점검했습니다. 이후 홈서버에서 Gemini 실행을 거쳐 로컬 Qwen 운영을 확인했습니다. 정확한 전환 시각과 모든 의사결정 사유가 기록된 것은 아니므로, 메모리 부족이나 API 비용을 유일한 이전 원인으로 단정하지 않습니다. 현재 비용 비교와 동시 접속 성능은 미측정입니다.

### 9 PWA 설치와 오프라인 이용도 가능한가요

현재 확인한 운영 소스와 실행 파일에서는 PWA manifest와 service worker를 찾지 못했고 설치 단말 검증도 완료하지 않았습니다. 모바일 브라우저 이용은 확인된 웹 기능으로 설명하고, 설치와 독립 창, 오프라인 지원은 별도 검증 항목으로 남깁니다.

### 10 이전 질문을 기억하거나 개인 일정을 관리하나요

현재 API는 질문 한 건을 기준으로 검색하고 답합니다. 화면의 대화 기록이 서버의 대화 기억을 뜻하지는 않습니다. 로그인, 개인 일정, 알림은 현재 발표 범위에 포함하지 않으며, 검색과 근거 전달의 품질을 먼저 개선합니다.

### 11 테스트 통과 수를 발표 본문에서 뺀 이유는 무엇인가요

10월 9일에는 당시 로컬 확장본의 대표 검색 6건과 회귀 검사 163건 통과 기록이 있고, 10월 18일 별도 선별 검사에서는 58건 중 57건 통과와 1건 실패 기록이 있습니다. 검사 날짜와 대상이 다르며 생성 답변의 종합 정답률을 뜻하지 않습니다. 실패 1건도 사전 로드 여부와 health의 문서 수 기대값 차이였으므로 운영 DB 손실로 해석하지 않습니다.

### 12 기존 발표의 90퍼센트는 달성한 수치인가요

기존 자료의 90퍼센트는 향후 평가 목표였습니다. 현재 달성 실적으로 사용하지 않습니다. 같은 질문과 정답 근거를 고정하고 모델, 자료 버전, 검색 결과와 생성 답변을 함께 저장한 뒤 정확도를 평가할 계획입니다.
