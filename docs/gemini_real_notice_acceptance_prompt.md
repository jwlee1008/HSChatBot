# 다음 구현 라운드 — 실제 공지 형식 지원

`docs/campusmate_acceptance_phase1_20260925.md`를 읽고 실제 공지 기반 추출을 개선해줘. repair4 승인 사항은 유지한다. 이번 범위는 실제 공지 형식 지원이며 배포/운영 알림은 별도 과제다.

## 목표

`tests/fixtures/real_notice_acceptance_cases.json`의 네 실제 문서에서 목표 일정이 추출되고, 무일정 대조군은 0건이어야 한다. 원문은 문서 ID로 조회하고 공백/줄바꿈을 임의로 재작성한 합성 문장만 테스트하지 마.

- `2026. 9. 10.(목)`, `09. 11.(금)`, `9/10(목)` 등의 점/슬래시 날짜, 요일 괄호, `~`/`∼`, 표·줄바꿈을 처리해.
- 신청/보증금/시험/운영 기간을 구분하고 날짜를 해당 항목의 제목과 연결해. 일괄 평탄화로 서로 다른 행이나 단계의 날짜를 합치지 마.
- 원문에 없는 연도·시각은 근거 없이 확정하지 마. 연도 추론과 모호성은 일관된 정책으로 표시해.
- 제목/본문 날짜 충돌과 24:00 같은 경계 표현은 명시적으로 확인을 요청해. TOPCIT 보증금 마감의 정확한 13:00과 다른 단계의 경계를 섞지 마.
- 정규화 전후 원문 위치를 보존해 source_quote는 실제 입력 구간이어야 해. 날짜 유효성 공통 게이트와 기존 정밀도/BOLA/confirmed 계약을 유지해.
- 검색 청크 최대 2,000자라는 제한을 유지하되 부분 청크로 전체 공지를 처리했다고 보고하지 마. 전체 본문 평가와 실제 카드 청크 평가를 구분해.

## 검증

1. 기존 150개 핵심 회귀를 유지해.
2. `PYTHONPATH=. .venv/bin/python scripts/verify_real_notice_acceptance.py`의 목표값을 약화하지 말고 통과시켜. 추가 후보의 날짜·제목·근거도 수동 점검해.
3. 날짜/제목/연도를 바꾼 미학습 변형도 추가해. 문서 ID나 특정 제목별 정답 상수를 넣지 마.
4. 실제 공지 본문을 가진 출처 카드에서 추출 → 목표 후보 선택 → 검토 → 저장 → 재조회가 되는지 Chromium으로 확인해. RAG 응답 전달을 mock하면 명시하고 추출 API는 mock하지 마.
5. 취소/미선택/추출만 수행할 때 미저장, 실패 시 수동 등록 가능 여부도 확인해.

임시 DB를 사용하고 data 파일 전후 SHA-256을 대조해. 외부 LLM/크롤링/배포/커밋/푸시는 하지 마. 애플리케이션 전면 재작성이나 운영 알림 확장은 범위 밖이다.

완료 후 `docs/gemini_real_notice_acceptance_report.md`에 원문별 기대/실제 결과, 변형 검증, 브라우저 실행 결과, 남은 제한을 기록해. 이는 에이전트 사전 수용 검사이며 실제 재학생 UT 완료라고 쓰지 마.
