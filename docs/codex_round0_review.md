## 1. [P1] 정답표에 원문과 다른 금액·근거 없는 요건이 포함됨

대상: `docs/campusmate_evaluation_baseline.md:57` 이후 대표 사례.

- 사례 6은 TOPCIT 보증금을 1만원으로 적었지만 로컬 공지 224626 본문은 **보증금 20,000원**, **응시료 지원 10,000원**을 별도로 명시한다. 잘못된 금액을 답해야 통과하는 평가가 된다.
- 사례 3의 근거로 지정한 6234 페이지는 졸업 및 학위수여 안내이며 제시한 졸업유예 자격의 근거가 아니다. 로컬에 별도 6237 졸업유예 페이지가 있으며 외국인 유학생·수료자·조기졸업 신청자 제외 등을 명시한다. 제시한 건축학부 10학기 등의 조건을 해당 근거에서 확인하지 못했다.
- 사례 4의 ‘편입생은 3개 학기 이내’는 지정한 6248 본문에 없다. 확인되지 않은 예외를 정답 조건으로 넣지 않는다.
- 사례 7은 제목/본문 날짜 충돌을 확인할 수 있지만 ‘과거 공지 오기’, ‘본문 정정’이라는 편집 이력은 확보된 내용만으로 확정할 수 없다. 관찰 사실과 추정을 구분한다.

10개 사례를 모두 다시 대조하고 각 주장에 문서 ID·URL·원문 발췌·입력 파일 해시를 붙인다. 근거가 없거나 OCR 확인이 필요한 주장은 미확정으로 남긴다. 이는 현재 학교 규정을 새로 검증한 것이 아니라 저장된 데이터와 평가 정답표의 일치 검수다.

## 2. [P1] 사용자 확인 정책 위반 및 모호한 마감의 임의 확정

대상: `tests/fixtures/schedule_extraction_cases.json` 및 정합성 테스트.

- sched-01, 04, 05, 09, 10, 14, 15, 18, 19는 후보가 있는데 `requires_user_confirmation: false`다. 원래 요구는 모든 추출 후보를 사용자가 확인한 뒤 저장하는 것이다. 정보의 모호함과 저장 전 사용자 확인은 서로 다른 개념이다.
- sched-20은 자정이 모호하다면서 `2026-10-09T23:59:59+09:00`을 정답 필드에 넣었다. 10월 9일 00:00인지 그날 종료 경계인지 확정할 수 없으며 23:59:59를 만들어 넣으면 안 된다. 날짜 표현은 보존하되 확정 timestamp는 null, 해석 선택지는 별도 필드로 둔다.
- sched-18의 `source_quote`는 생략 부호를 삽입한 재작성 문자열이다. 추적 가능한 원문 발췌 목록 또는 정확한 부분 문자열로 보존한다.
- 현재 테스트는 boolean 타입과 ‘true이면 모호성 사유 필수’만 확인한다. 모호하지 않아도 확인은 필수여야 하므로 정책 자체를 검증하도록 수정한다.
- 취소 사례가 없는데 완료 보고서는 취소/연장을 다룬다고 적었다. 취소 사례를 추가하거나 보고를 정정한다.

## 3. [P2] 날짜 파서의 허용 범위 회귀 및 잘못된 입력 수용

대상: `scripts/build_unified_dataset.py:69-89`, `tests/test_date_parsing.py:122`.

현재 직접 재현:

| 입력 | 현재 결과 | 요구 |
|---|---|---|
| `2026-09-23T15:00:00+09:99` | `2026-09-23 04:21:00+00:00` | 잘못된 offset 분 99를 거부 |
| `2026-09.23` | 정상 날짜 | 혼합 구분자는 명시한 지원 형식이 아니므로 거부 |
| `20260923` | None | HEAD 파서는 정상 처리했던 ISO 기본 형식. 호환성 유지 |
| `2026-09-23T15:00:00+0900` | None | HEAD 파서는 UTC 06:00으로 정상 처리. 호환성 유지 |

HEAD 함수만 AST로 추출하여 기존 두 형식의 동작을 별도로 확인했다. 운영 데이터 변경은 없다. 기존 ISO 경로를 제거하고 직접 정규식/offset 계산으로 바꾸면서 지원 형식이 줄고 잘못된 offset은 timedelta에 의해 정상화된다. 정상 입력 호환성과 엄격한 잘못된 입력 거부를 함께 검증해야 한다. 현재 `20260923`을 garbage로 규정한 테스트도 수정한다.

## 4. [P2] R1 계약에 날짜-only를 보존할 필드가 없음

대상: `docs/campusmate_evaluation_baseline.md:213-217`.

fixture는 `2026-09-25` 같은 date를 사용하지만 저장 계약에는 nullable datetime인 start_at/end_at만 있다. 양쪽을 null로 저장하면 날짜를 잃고 datetime으로 저장하면 시각을 발명한다. date 필드와 datetime 필드, 시간대 및 조합 제약을 명시한다. 시작만 있는 약속, 날짜-only 마감, 시작 날짜만 알려진 기간, 종일 일정, 추출 초안을 구분하고 아직 확정되지 않은 후보는 저장 API의 확정 일정과 분리한다. DB/API 구현은 후속 R1에서 한다.

## 보고 정확성 보완

- 평가 상태는 실행 모드(mock/live), 호출 결과(success/api_error/not_run/no_call), 정답 판정(pass/fail/needs_review)을 구분하면 혼동을 줄일 수 있다. 현재 4대 상태 표에는 FAIL이 빠져 있고, LLM을 부르지 않고 올바르게 유보한 결과를 표현하지 못한다. 문서 수준에서 정의하고 평가기 구현 변경은 하지 않는다.
- ‘timedelta 누락’은 기존 결함이 아니다. 기존 함수는 timedelta를 쓰지 않았으며 이번 수동 offset 구현으로 새로 필요해졌다.
- 원래 HEAD에서 garbage 입력은 re 미정의로 중단한다. import만 보충한 중간 상태의 부분 일치 재현과 원래 상태 재현을 구분한다.
- 54개는 지정된 회귀 테스트 통과이며 전체 서비스 검증이 아니다. 실제 LLM 호출·서비스 DB·배포를 이번 검수에서 검증하지 않았다.
