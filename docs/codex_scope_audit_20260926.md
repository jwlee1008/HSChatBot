# 원래 챗봇 대비 범위·배포 흐름 감사 — 2026-09-26

## 결론

Cloudtype에 배포된 챗봇을 기준으로 이번 작업은 단순 품질 개선을 넘어 **인증·개인 일정 관리 제품으로 상당히 확장**됐다. 기존 챗봇은 남아 있으나 변경량의 중심은 신규 일정 기능이다. 반면 9월 23일에 작성된 개선 계획 자체를 기준으로 보면 인증→일정→캘린더 구현은 그 계획을 따른 것이다. 즉 가장 큰 범위 전환은 Gemini 수정 루프 중 우연히 발생한 것이 아니라, 개선 계획 수립 시점에 들어갔다.

문서가 존재한다는 사실과 사용자가 해당 범위 전환을 명확히 승인했다는 사실은 다르다. 현재 자료로 PRD의 작성 경위나 사용자의 최초 명시적 승인까지 확정할 수 없다. 반복된 '계속 진행'만으로 사용자에게 제품 방향 전환이 충분히 설명됐다고 판단해서도 안 된다.

## 비교 기준 및 방법

- 기준: Cloudtype 실제 적용 커밋 `34a1eaad84aec0b4e3dc65eb8c8358bbb05f00b5`. 현재 로컬 HEAD와 같다.
- 이 커밋의 실제 React/FastAPI 코드와 현재 작업 트리를 비교했다. README의 Streamlit 등 설명은 낡았으므로 실제 코드를 우선했다.
- 계획·프롬프트·검수 보고서로 범위 유입 경로를 추적했다. 이번 감사는 새 테스트나 실제 LLM 품질 평가를 실행한 것이 아니다.
- 추적 파일 diff만으로 신규 모듈이 누락되지 않도록 untracked Python 파일도 확인했다. 코드 줄 수는 시간/품질/완성도 비율을 뜻하지 않는다.

## 개인 일정 기능의 유입 경로

1. `.prd_work/build_prd.py`는 CampusMate를 과제·시험 일정 통합 관리 서비스로 기술한다. 로그인, 일정 CRUD, 정보 추출, 사용자 확인, 캘린더, 마감 알림을 MVP로 명시한다. 이는 PRD 생성 소스의 내용이며 최종 DOCX 전체나 작성·승인 경위를 이번 감사에서 대조한 것은 아니다.
2. `docs/campusmate_improvement_plan_20260923.md`는 이 소스를 근거로 개선 목표를 '학교 정보를 답하고 사용자가 확인한 일정을 개인 캘린더에 저장'으로 확장했다. 인증/일정, 추출, 캘린더가 2~4순위가 됐고 검색 품질·데이터 최신성·자동 반영은 뒤로 밀렸다.
3. `docs/gemini_round1a_prompt.md`는 Codex 설계 결정으로 로컬 SQLite 인증/세션을 지시했다. PRD 소스의 PostgreSQL과 달리 운영 PostgreSQL 전환은 후속으로 미뤘다.
4. `docs/gemini_round1b_prompt.md`는 개인 일정 CRUD를 명시적으로 지시했다. 이후 R2 추출, R3 캘린더가 연결됐다.
5. 이후 다수의 수복 루프는 새 기능에서 생긴 422 저장 실패, 고정 날짜 반환, 로그아웃 미폐기, 서울 시각 왜곡, 정밀도 손실, 기간/연도 파싱 결함 등을 수정했다. 기존 챗봇이 원래 갖고 있던 문제를 계속 고친 것과 구분해야 한다.

## 변화의 규모와 챗봇 품질의 실제 차이

- `frontend-web/src/App.tsx`: 567줄 → 2,271줄, 약 4배. 주로 인증 모달/일정 모달/캘린더/상태 관리 추가.
- 신규 backend/auth, db, routers, schedules: Python 파일 13개, 합계 3,969줄(초기화 파일 포함).
- `backend/schemas.py`: 433줄 추가, 1줄 삭제. 주로 계정/일정 계약.
- `core/rag.py`: **1줄 추가**. 출처에 본문 content를 실어주는 변화이며 검색 순위나 생성 프롬프트 개선이 아니다.
- core의 다른 파일, crawler, .github, 추적 중인 data 파일: 기준 커밋 대비 변경 없음.
- 3,447청크 통합 지식베이스는 기준 커밋에 이미 들어 있었다. 이번 일정 작업의 신규 성과가 아니다.
- 159개 테스트 통과는 선택된 회귀/신규 기능/백업 검사 결과다. '챗봇 답변 159개가 좋아졌다'는 뜻이 아니다. RAG 10/10은 원문 대조, 실제 공지 5/5는 일정 추출의 최소 수용 검사다.
- 결론: 기능·저장·UI 규모는 크게 확장됐지만, 이 기간에 챗봇 답변 품질이 얼마나 좋아졌는지는 실측되지 않았다. 개선율을 숫자로 제시할 근거가 없다.

## 왜 바로 Cloudtype에 올라가지 않았나

R0/R1 프롬프트는 commit/push/실배포를 명시적으로 제외했다. 구현과 검수를 분리한 결정이었으나, 검수 통과 후 실제 배포까지 연결하는 단계가 계속 남았다. 로컬 SQLite 선택과 Cloudtype 저장 제약을 처음부터 맞추지 않았고, 이후 검증도 ARM64 로컬 Docker에서 진행돼 Cloudtype용 검증과 달라졌다. 이는 사용자에게 명확히 설명했어야 하는 설계·진행상의 공백이다.

원래 계획도 일정 흐름 완성 후 이른 검증 배포를 요구했다. 실제로는 수정·테스트 루프가 먼저 누적됐다. 또한 '전체 개선 마일스톤 완수'라는 일부 보고서 표현은 검색 품질/정보 보강/운영 반영/예약 알림까지 완료된 듯한 오해를 만들었으며, 후속 Codex 검수에서 전체 승인 불가·부분 구현으로 정정한 기록이 있다.

Cloudtype 실제 환경의 세부 확인은 `codex_cloudtype_assessment_20260926.md`에 별도 기록했다. 여기서 새 외부 작업이나 설정 변경은 하지 않았다.

## 원래 흐름으로 복귀하는 제안

사용자가 원하는 기준이 '기존 챗봇 개선 후 Cloudtype 업데이트'라면 다음 출시 범위를 그 기준으로 다시 고정한다.

1. 현재 확장 코드는 삭제하지 않고 보존한다. 배포판에서 인증/일정/캘린더를 분리하거나 비활성화한다. 화면만 숨기는 것으로 끝내지 말고 서버 startup의 SQLite 의존성과 라우터도 분리해야 한다.
2. 기존 챗봇 결함 수정 및 Cloudtype 배포에 필요한 변경만 검토해 배포용 변경 묶음을 만든다. 챗봇만 배포할 때 개인 일정 DB가 필수라는 앞선 설명은 해당하지 않는다.
3. 대표 질문의 실제 답변/근거/응답시간을 기존 기준과 비교해 챗봇 품질 개선을 별도로 입증한다. 외부 모델 호출은 실행 범위와 비용을 정한 뒤 한다.
4. Cloudtype의 실제 Python/Docker 빌드 경로·메모리·모델 초기화·환경변수를 확인하고 선택한 버전의 커밋/배포를 명시적인 단계로 연결한다. 로컬 통과를 배포 완료라고 부르지 않는다.
5. 개인 일정 확장은 이후 선택 기능으로 재검토한다. 지금까지 만든 기능을 폐기할 이유는 없지만 원래 챗봇 출시의 선행 조건으로 둘 이유도 없다.

이 문서는 감사와 제안이며 기능 제거·분리·commit/push·재배포는 아직 실행하지 않았다.
