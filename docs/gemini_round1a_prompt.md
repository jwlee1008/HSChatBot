## 이번 설계 결정

1. 로컬 MVP의 계정/세션 저장은 파일 기반 SQLite로 시작한다. Chroma와 별도 DB이며 경로를 설정으로 주입한다. 테스트에서는 임시 디렉터리 DB를 사용한다. 운영용 PostgreSQL 전환은 후속 작업이고 이번에 두 DB를 모두 지원할 필요는 없다.
2. username은 일반 로그인 ID다. 학번이나 학교 이메일 소유권을 검증했다고 주장하지 않는다. ID의 공백·대소문자 정규화, 길이 제한과 중복 정책을 문서화하고 DB UNIQUE 제약으로 동시 등록 충돌을 처리한다.
3. 비밀번호는 검증된 라이브러리의 password hashing을 사용한다. 직접 암호 알고리즘을 구현하지 마라. 라이브러리 선택 시 공식 문서/현재 설치 환경을 확인하고 필요한 의존성만 명시한다. 평문/해시를 응답 또는 로그로 내보내지 않는다. 최소/최대 길이와 긴 Unicode 비밀번호 처리 정책을 테스트한다.
4. R0의 JWT 초안 대신 이번에는 **서버 저장형 opaque bearer 세션 토큰**을 사용한다. 충분한 암호학적 난수로 만들고 DB에는 토큰 해시만 저장한다. 만료 시각을 UTC로 기록하고 모든 인증 요청에서 만료/폐기를 확인한다. 기본 만료는 24시간이며 설정 가능하게 한다. refresh token과 소셜 로그인은 만들지 않는다.
5. 클라이언트가 Authorization: Bearer 헤더로 전송하는 API다. 이번에는 쿠키 인증·프론트엔드 토큰 저장을 구현하지 않는다. 실제 프론트엔드 연동 및 공개 서비스 인증 강화는 별도 검수한다.

## API 계약

| Method | 경로 | 동작 |
|---|---|---|
| POST | /api/v1/auth/register | username/password JSON으로 계정 생성, 201. id/username/created_at 등 공개 사용자 정보만 반환. 자동 로그인하지 않음 |
| POST | /api/v1/auth/login | JSON 자격 증명 검증, 200. access_token, token_type=bearer, expires_at 반환 |
| GET | /api/v1/auth/me | 유효 bearer 토큰으로 본인 공개 정보 조회, 200 |
| POST | /api/v1/auth/logout | 현재 세션 폐기, 204. 같은 사용자의 다른 세션은 유지 |

중복 username은 409, 잘못된 입력은 422, 잘못된 자격 증명/누락·만료·변조·폐기 토큰은 401로 처리한다. 존재하지 않는 사용자와 비밀번호 오류는 동일한 안전한 로그인 실패 문구를 반환한다. client가 user_id/role/created_at 등을 주입할 수 없도록 입력 스키마를 제한한다. 토큰 응답에는 Cache-Control: no-store를 적용한다. DB 오류나 원시 예외를 HTTP 응답에 포함하지 않는다.

## 저장·모듈 경계

- users와 sessions 테이블 및 최소한의 버전 있는 migration/init 경로를 만든다. 임의 drop/reset 동작은 넣지 않는다. 초기화를 반복해도 기존 사용자/세션을 보존한다.
- user id는 서버 생성 UUID. sessions에는 사용자 연결, 토큰 해시, created_at/expires_at 및 폐기 표현을 저장한다. 외래키 적용과 트랜잭션을 사용한다.
- 인증 라우터, DB 접근, 비밀번호/세션 처리, 공개/입력 스키마를 적절히 분리한다. 기존 RAG 파일에 인증 구현을 몰아넣지 마라.
- SQL은 매개변수 바인딩을 사용한다. 인증 의존성은 R1-B에서 current_user를 사용할 수 있게 제공한다.
- 서버를 새로 만들거나 프로세스를 재시작해도 파일 DB의 계정과 유효 세션이 유지되어야 한다. 런타임 SQLite 파일은 git에 포함하지 않는다. 설정 예시는 비밀값 없이 기록한다.
- 필요한 패키지만 requirements에 추가하고 전체 패키지 업그레이드나 기존 모델 설정 변경은 하지 않는다.

## 완료 기준과 테스트

mock 저장소만 사용하지 말고 임시 파일 SQLite와 실제 HTTP TestClient로 검증한다.

1. 회원가입 → 로그인 → me → 로그아웃 → 같은 토큰 401 흐름.
2. 중복/정규화 충돌 등록, 잘못된 비밀번호, 없는 사용자, 빈/과대 입력.
3. 헤더 누락·malformed·변조·만료·폐기 토큰 차단. 만료는 긴 sleep 대신 시계 주입 또는 저장 시각 조정으로 테스트한다.
4. 계정 A/B 각각 로그인했을 때 me가 항상 해당 본인을 반환. 같은 계정의 두 세션 중 하나만 로그아웃했을 때 다른 하나 유지.
5. 서버/앱 및 DB 연결을 새로 열어도 계정·유효 세션 보존. 반복 migration/init에도 데이터 유지.
6. DB에 평문 비밀번호/원문 세션 토큰이 없고 응답에 해시/원시 예외가 없는지 확인.
7. 기존 query/retrieve 응답 계약에 영향 없는 관련 mock 회귀 확인. 테스트에서 실 API/크롤링/운영 Chroma 접근이 일어나지 않아야 한다.

실행 전 관련 테스트의 외부 의존성을 확인하고 적절한 격리 테스트를 선택한다. 전체 테스트를 무작정 실행하지 말고 실행한 명령과 통과/실패 수를 정확히 보고한다. 새 테스트는 실제 행동·보존·접근 제어를 확인해야 한다.
