# Gemini R0 마무리 — 평가 근거만 보완

Codex가 수정본을 재검수했다. 코드 및 일정 후보 사용자 확인 정책은 통과했고 지정 회귀 64개를 재확인했다. 이번에는 `docs/codex_round0_revision_review.md`의 **남은 필수 수정 1~3번만** 해결한다. 날짜 파서/일정 fixture/신규 API/DB는 변경하지 마라.

## 수정할 내용

1. `docs/campusmate_evaluation_baseline.md` 사례 5의 상상파크 FAQ ID를 실제 문서와 연결하라. 올바른 ID는 `002c45a581276fc882ccebe30204c976f2cac668efbd727ba16ac05672a2564f`다. 잘못된 기존 ID도 실제 존재하므로 단순 존재 검사는 부족하다. 모든 사례에 대해 ID로 문서를 찾고 제목·URL·본문을 대조하라. 같은 FAQ 목록 URL에 여러 문서가 있음을 유의하라.
2. '정확한 원문 발췌'를 모두 실제 부분 문자열 또는 부분 문자열 목록으로 바꾸어라. 공백 정규화가 필요하면 규칙을 명시하라. 중간 문장을 제거한 발췌는 별도 항목으로 나누고, 내용을 바꾼 요약은 요약으로 표시하라. 특히 사례 8의 신청 대상 문장은 실제 원문을 복사하라.
3. 사례 2의 OCR 미검수 시각은 확정 채점 기준에서 제외하거나 NEEDS_REVIEW로 표시하라. 사례 7은 제목의 6월 11일 안내가 FAIL임을 명확히 하고 본문 기간과 충돌을 안내하도록 정리하라. 사례 10은 해당 기숙사·해당 주 정보의 미확보로 범위를 좁히고 질문 기준일을 고정하라.

## 검증 방법

문서 내용을 다시 손으로 추정해 채우지 말고 로컬 JSON을 읽어 근거를 추출하라. 재현 가능한 작은 읽기 전용 검사 스크립트 또는 구조화 근거 JSON을 추가해도 된다. 구조화 파일을 만들면 이 10사례에만 범위를 한정하고 공통 dataset hash, case id, document id, title, URL, quote list, 검수 상태를 기록하라. 근거가 없는 사례는 null/미확보 상태를 사용하며 출처를 만들지 마라.

검사 결과에는 ID-제목-URL 일치 여부, 모든 발췌의 실제 원문 포함 여부, 데이터 해시 일치 여부를 포함하라. 단순히 '전수 확인'이라고 적지 말고 실행한 명령과 실제 결과를 기록하라. 자동 검사는 내용의 사실성이나 OCR 정확도를 보증하지 않는다.

문서/근거만 바뀌었다면 기존 64개 테스트를 무조건 재실행할 필요는 없다. 이번에 추가한 근거 검증을 수행하고 이전 코드 검증과 구분하라.
