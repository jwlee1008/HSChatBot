## 최종 우선순위

| 순위 | 개선사항 | 이유 및 완료 기준 |
|---|---|---|
| 1 | 기존 결함 수정 + 평가 기준선 확정 | 날짜 파싱 오류를 재현 테스트로 수정. 핵심 질의·일정 추출 평가 항목과 데이터 버전을 고정. 실측·mock·미실행을 구분한다. |
| 2 | 계정·개인 일정 저장 기반 | 로그인, 사용자별 일정 CRUD, 완료·중요도, DB 마이그레이션. 다른 계정의 일정을 조회·수정·삭제하지 못하고 서버 재시작 후 보존되어야 한다. |
| 3 | 자연어/공지 → 일정 후보 추출 → 사용자 확인 | JSON 스키마 검증, 근거 문장·원문 URL, Asia/Seoul 기준, 누락 날짜·다중 일정·모호한 시간 처리. 날짜나 시간을 임의로 채워 저장하지 않고 사용자가 확정한다. API 장애 때 수동 입력 가능. |
| 4 | 최소 캘린더 통합 UI | 챗봇 출처에서 일정 후보 열기 → 수정 → 저장 → 월간/오늘 목록 표시 → 수정·삭제까지 실제 흐름 완성. 중복 클릭 저장 방지. 주간 뷰는 후속. |
| 5 | 핵심 정보의 최신성·첨부·시점 충돌 개선 | 수강·장학·졸업·휴복학·시설의 대표 질문으로 누락을 찾고 해당 자료부터 보강. 게시일/원문 수정일/확인일/적용 학기를 분리. 기간·대상·제외조건 청크를 함께 회수한다. |
| 6 | 작은 검증용 배포 + 마감 알림 | HTTPS 및 영속 DB 환경에서 먼저 전체 흐름 확인. D-2/당일 예약, 일정 수정·삭제 시 예약 갱신, 재시작 복구·중복 전송 방지. 권한 거부 시 앱 내 표시. 실제 대상 모바일 환경에서 알림 확인. |
| 7 | 하이브리드 검색 + 답변 근거 검증 | BM25 후보와 벡터 후보를 결합하고 동일 문서 중복을 제거. 약어·정확한 명칭·연도/학기 조건·정정 공지를 평가. 기존 대비 정답 근거 회수율과 오답 변화로 채택한다. |
| 8 | 자동 수집 → 통합 → 색인 → 서비스 반영 | 기존 Actions 확장. 변경 해시, 실패 재시도, 이전 성공본 보존, 새 버전 검증 후 전환·롤백. 실행 서버의 데이터 버전이 실제 바뀌었는지 확인한다. |
| 9 | 수집 범위 확장 및 제한된 과거 백필 | 캠퍼스/부서/전공 및 공개 도서관 자료 중 실제 질문이 있는 항목부터 확대. 주요 게시판과 최근 1년을 1차 범위로 제안하고, 필요에 따라 2~3년 확대. 게시판별 수집 기간·종료 이유·실패 목록을 기록한다. |
| 10 | 탐색 UI·접근성·운영 공개 마무리 | 공지/안내 브라우저, 출처 유형·갱신일·첨부 상태, 모바일 입력·키보드 접근성. 재학생 10명 이상 UT 후 치명 결함 해결, 운영 복구 확인 후 공개한다. |

순위는 착수 우선순위다. 사용자 테스트 모집과 알림 기술 검증은 일찍 시작한다. 5·7·8·9번을 모두 끝낼 때까지 2~4번을 미루지 않는다. 치명적인 오답·타인 일정 노출·데이터 손실은 발견 즉시 다른 작업보다 먼저 처리한다.

## 첨부안에서 조정할 사항

1. **건수 중심 목표 교체:** 250페이지·2,500공지·7,000청크는 추정 규모다. 완료 기준은 핵심 질문에 답하는 근거 확보율, 최신성, 수집 누락·실패의 추적 가능성으로 둔다.
2. **본문 100%·무결점 OCR 목표 교체:** 암호화·비지원·빈 원문은 별도 상태로 남긴다. 모든 대상의 처리 결과를 기록하고, 핵심 질의 관련 추출문을 표본 검수한다. 추출 성공과 정확도를 구분한다.
3. **연도 지정은 해당 연도 우선:** “2024년” 질문을 최신 공지로 대체하지 않는다. 질문의 적용 연도·학기와 게시일을 구분한다. 연도 없는 질문도 단순 게시일 최신순으로 상시 규정을 밀어내지 않는다.
4. **일정 시간 모델을 먼저 정한다:** 날짜만 있는 마감, 확정 시각, 종일 일정, 시작/종료 기간을 구분한다. 과목명은 선택값이고 추출 근거와 사용자 수정 결과를 보존한다.
5. **알림 구현 범위 분리:** Notification API 표시만으로 백그라운드 마감 예약이 완성되지 않는다. 서버 예약·Push·service worker와 권한/구독 관리를 검토한다. 모바일은 persistent notification이 필요하다는 [MDN 설명](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API)과 [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)를 기준으로 대상 기기를 검증한다.
6. **배포는 마지막 하루 작업이 아니다:** 일정 흐름이 완성되면 검증용 배포를 먼저 하고, 로그인·저장·알림을 실제 환경에서 확인한다. 공개 배포 전 UT/복구 검증을 수행한다.
7. **외부 Google/Outlook 캘린더 동기화는 후속:** 우선 서비스 내부 개인 캘린더를 완성한다. 외부 동기화·소셜 로그인·주간 뷰·광범위 전수 OCR은 핵심 흐름 뒤에 둔다.

## 검증 기준 제안

- RAG: 초기 30~50문항. 5대 주제 외에 약어·과거 연도·최신 정정·본문 미확보·범위 밖 질문 포함. 정답 근거 Recall@5, 답변의 출처 지지 여부, 날짜/대상 혼입, 유보 적절성을 분리 측정한다. 평가에 사용하지 않은 질문도 남겨 둔다.
- 일정: 최소 20사례. 정확한 날짜, 상대 날짜, 연도 누락, 시각 누락, 여러 마감, 취소/정정, 잘못된 날짜를 포함한다. 초안 단계는 누락을 표시할 수 있지만 사용자 확인 없는 저장은 허용하지 않는다.
- 사용자 격리: 계정 A가 B의 일정 ID로 조회/수정/삭제할 수 없어야 한다.
- 속도: 검색·생성·전체 응답, cold/warm, 성공·실패를 분리한다. 3초 목표는 전체 응답 p95 등 측정 정의를 정한 뒤 검증한다. 미호출 0초를 성능에 넣지 않는다.
- UT: 10명 이상, 입력→확인→저장→조회→수정/삭제→알림 과업을 관찰. 만족도 4.0/5 이상은 목표이며 예상 달성값이 아니다. 마감 오저장·타인 데이터 노출 등 치명 결함 0건을 공개 조건으로 둔다.
- 추출/검색 시험은 기본 mock·fixture로 돌리고, 실제 모델 호출은 소규모 최종 확인에 사용한다. 구현용 Gemini 사용량과 서비스 Gemini API 한도는 별도로 취급한다.

## 진행 방식: Codex 총괄 → Gemini 구현 → Codex 검수

1. Codex가 한 라운드의 목표·수정 범위·완료 기준·테스트·금지 범위를 담은 프롬프트를 만든다.
2. 사용자가 Gemini에 전달한다. Gemini는 한 라운드만 구현하고 변경 파일, 실행 명령/결과, 미검증 사항을 보고한다.
3. 사용자가 완료 보고와 작업 위치를 전달한다. 동일 로컬 저장소면 Codex가 실제 diff를 확인하고, 다른 환경이면 patch/commit 및 보고서로 검수한다.
4. Codex가 재현·회귀 검사를 하고 통과/수정 필요를 판정한다. 통과 전에는 다음 기능을 쌓지 않는다.
5. 미달이면 수정 프롬프트, 통과하면 다음 라운드 프롬프트를 제공한다. 장기 프롬프트를 한 번에 모두 확정하지 않는다.

각 라운드는 독립적으로 검수 가능한 크기로 나눈다. 예: R0 날짜 결함/평가 기준 → R1 인증/일정 API → R2 일정 추출 → R3 확인/캘린더 UI → R4 핵심 정보 보강 → R5 검증용 배포/알림 → R6 검색 → R7 자동 반영 → R8 범위 확대/UT/공개 마무리. 큰 라운드는 다시 분할한다.

원안의 14일은 확정 일정으로 사용하지 않는다. 최초 2라운드 소요 시간과 남은 제출 기한을 보고 재산정한다. 기한이 짧으면 전수 백필·주간 뷰·외부 캘린더 동기화부터 줄인다.

## 이번 검토 범위

애플리케이션 코드는 수정하지 않았다. 로컬 코드·JSON·기존 검토 보고서 확인, mock 회귀 30개 실행, 날짜 파싱 결함 재현 및 계획 문서/첫 프롬프트 작성만 수행했다. 전체 테스트, 실제 로그인/일정 흐름, 실 API 답변, 운영 배포 상태는 이번에 검증하지 않았다.
