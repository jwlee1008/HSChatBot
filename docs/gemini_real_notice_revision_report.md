## 2. N1~N3 항목별 결함 원인, 수정 내용 및 검증 결과

### N1 (P1): 범위 추출 시 잘못된 시작 시각 정상화 오류 방지 및 대칭 보류

- **결함 원인:**
  `backend/schedules/extraction.py:594–600, :629`에서 `has_start_time and s_hr < 24` 조건이 거짓일 경우 시작 시각(`s_hr`)을 날짜 전용 일반 문자열(`YYYY-MM-DD`)로 축소하고 `is_time_confirmed=True`, `is_ambiguous=False`로 후보를 생성했습니다. 이로 인해 `25:90`, `25:00`, `23:90` 등의 무효 시각이 공통 검증 게이트(`_validate_and_normalize_candidates`)에 도달하기 전에 시각 정보가 유실되어 정상 일정처럼 둔갑하는 문제가 발생했습니다.
- **수정 내용:**
  1. 시작 시각과 종료 시각을 완벽히 대칭적인 구조로 분리하여 처리하도록 파서를 개편하였습니다.
  2. `24:00` 자정 경계 표현은 시작/종료 모두 명시적으로 `is_ambiguous=True`, `unconfirmed_fields=["time", "exact_boundary"]`, `ambiguity_reason="24:00 경계 표현은 당일 23:59:59와 익일 00:00 등 해석 차이가 존재하여 확인 필요"`로 처리하였습니다.
  3. `25:90`, `25:00`, `23:90` 등의 잘못된 시각 토큰은 원형의 ISO 문자열(`...T25:90:00+09:00`)을 유지하여 공통 검증 게이트로 온전히 전달하도록 보존하였습니다.
  4. 공통 검증 게이트(`_validate_and_normalize_candidates`)에서 시작 시각 오류(`has_start_time_error`)와 종료 시각 오류(`has_end_time_error`)를 각각 판정하여, 오류가 발생한 측의 확정 필드(`start_datetime`, `start_date` 또는 `end_datetime`, `end_date`)를 `None`으로 비우고 `is_time_confirmed=False`, `is_ambiguous=True`, `unconfirmed_fields`에 `"time"`을 추가하도록 수정하였습니다.
- **검증 결과 (`test_n1_symmetric_invalid_and_boundary_time_handling`):**
  - 시작 시각 `25:90`, `25:00`, `23:90`, `24:00` 4종 전수 검증: `start_datetime=None`, `is_time_confirmed=False`, `is_ambiguous=True`, 모호 사유 표기 정상 확인.
  - 종료 시각 `25:90`, `25:00`, `23:90`, `24:00` 4종 대칭 검증: `end_datetime=None`, `is_time_confirmed=False`, `is_ambiguous=True`, 모호 사유 표기 정상 확인.

### N2 (P2): 기간 후보 공존 시 단일 일정 누락 해소 및 TOPCIT 4단계 회수

- **결함 원인:**
  `backend/schedules/extraction.py:639`에 위치하던 `if not candidates:` 조건문으로 인해, 문서 내에 기간 일정(Range)이 1건이라도 존재하면 단일 일정(Single Date/Deadline) 추출 블록이 아예 실행되지 않았습니다. 이로 인해 접수 기간과 면접 일시가 함께 있는 공지에서 면접 일정이 누락되고, 실제 TOPCIT 정기평가 공지에서 1~3단계(기간) 외에 4단계 `10. 10.(토) 9:30 ~ 12:00 [시험 응시]`가 누락되었습니다.
- **수정 내용:**
  1. `if not candidates:` 가드를 제거하고, 이미 기간 파서에서 채택된 원문 구간(`matched_spans`)과의 오버랩(`sp[0] <= rsp[1] and sp[1] >= rsp[0]`)만 정밀하게 배제하도록 변경하였습니다.
  2. 단일 날짜 아래 시간 범위를 갖는 구조를 처리하기 위해 `_INTRADAY_RANGE_RE` 파서를 신설하였습니다. 이를 통해 TOPCIT 4단계 `10. 10.(토) \n 9:30 ~ 12:00`을 정확하게 시작 `09:30`, 종료 `12:00`으로 회수하였습니다.
  3. 시험 시간(`9:30 ~ 12:00`)과 안내 텍스트에 포함된 입실완료 시간(`- 고사실 입실완료 9:10`) 및 문의처 전화번호(`02-760-4200`)가 일정으로 오인되는 것을 방지하도록 정규식 경계 및 숫자 경계 가드를 강화하였습니다.
  4. 종료 시각이 명시되지 않은 단일 이벤트(`면접 일시: 2027. 11. 8.(월) 14:00`)는 인위적으로 종료 일시를 생성하지 않고, `start_datetime="2027-11-08T14:00:00+09:00"`, `end_datetime=None`, `end_date=None`, `unconfirmed_fields=["end_time"]`, `is_ambiguous=True`로 정확히 추출하였습니다.
  5. 이미 기간 후보가 존재하는 문서에서는 `line_prefix`에 명시적인 항목명(예: `면접 일시: `)이 있는 경우에만 추가 단일 일정을 채택하고, 서식 없는 날짜 파편이나 세부 안내 번호는 중복 노이즈로 생성되지 않도록 안전 장치를 마련하였습니다.
- **검증 결과 (`test_n2_period_and_single_event_coexistence_and_topcit`):**
  - `접수 기간: 11.1~11.5` + `면접 일시: 11.8 14:00` 입력 시: 접수 기간(1건)과 면접 일시(1건, `end_datetime=None`, `unconfirmed_fields=["end_time"]`) 2건 모두 정상 회수.
  - 실제 TOPCIT 공지 전수 대조 시: 1단계(회원가입), 2단계(정보등록), 3단계(보증금납부), 4단계(시험응시 09:30~12:00) 4개 후보 정확 회수. `09:10` 입실완료 혼동 0건.

### N3 (P2): 출처 카드 제목 계약 연결, 오경고 제거 및 멘토링 충돌 브라우저 검증

- **결함 원인:**
  1. `frontend-web/src/App.tsx:1927`의 `handleExtractSchedule`에서 백엔드 `/api/v1/schedules/extract` 호출 시 `source_title`을 전달하지 않아, 별도 제목이 있는 실제 공지(멘토링 등)에서 제목-본문 간 일시 충돌을 비교할 수 없었습니다.
  2. `ScheduleExtractionRequest` 스키마에 `source_title`이 누락되어 클라이언트가 전송할 경우 `extra="forbid"`에 의해 거부되었습니다.
  3. `backend/schedules/extraction.py:407`의 정규식 `re.findall(r"(\d{1,2})[./](\d{1,2})")`이 연도 `2027.11.01`의 `27.11`을 월/일로 잘못 추출하여, 제목과 본문이 완전히 동일한 날짜임에도 허위 충돌 경고를 발생시켰습니다.
- **수정 내용:**
  1. **스키마 및 계약 연결:** `backend/schemas.py`의 `ScheduleExtractionRequest`에 `source_title: str | None = Field(default=None)`을 추가하고 `extra="forbid"` 설정을 엄격히 유지하였습니다.
  2. **라우터 및 프론트엔드 연동:** 라우터에서 `source_title`을 추출 엔진에 전달하고, `frontend-web/src/App.tsx`의 `handleExtractSchedule`에서 출처 카드의 `title`을 `source_title` 페이로드로 전송하도록 연결 후 프로덕션 빌드를 완료하였습니다.
  3. **날짜 파서 통일:** 본문 파싱에 사용하는 `_SINGLE_DATE_RE`를 제목 파싱에도 동일하게 적용하여, `2027.11.01`에서 연도 `2027`과 월 `11`, 일 `01`을 정확히 인식하도록 수정하였습니다. 이로써 제목과 본문의 일정이 동일할 때 거짓 충돌 경고가 발생하지 않습니다.
  4. **실제 멘토링 충돌 검출:** 실제 멘토링 공지(`1a676b27...`) 제목의 `(9.10.목~6.11.목 15:00)`과 본문의 `2026. 09. 10.(목) ~ 2026. 09. 17.(목) 15:00` 간의 날짜 불일치(`6.11` vs `9.17`)를 정확히 감지하여 `is_ambiguous=True`, `ambiguity_reason="공지 제목의 기간과 본문 신청 기간이 상이하여 확인 필요"`를 부여하였습니다.
- **검증 결과 (`test_n3_source_title_contract_and_conflict_check` & Chromium E2E):**
  - `extra="forbid"` 검증: 임의 필드 주입 시 `422 Unprocessable Entity` 정상 차단.
  - 동일 날짜 일치 검증: `프로그램 모집 안내 (2027.11.01 ~ 2027.11.05)`와 본문 `2027.11.01 ~ 2027.11.05` 비교 시 `is_ambiguous=False`, 경고 없음 확인.
  - 실제 멘토링 충돌 검증: 백엔드 API 및 Playwright Chromium E2E 브라우저(`test_mentoring_real_notice_title_conflict_browser_flow`)에서 출처 카드 클릭 시 모달 내 `⚠️ 모호성 안내 (확인 필요)` 배너 표출 확인.
  - Zero-Auto-Save 확인: 모달이 열려 있는 상태 및 취소 클릭 후 DB 레코드가 0건으로 유지됨을 브라우저 수준에서 증명.

## 4. 미해결 항목 및 향후 운영 권장 사항

1. **학사일정 목록의 월별 중복 후보 병합 (후속 품질 과제):**
   - 현재 78개의 학사일정 후보는 원문 공지의 월별(9월, 10월, 11월...) 반복 게재 형식을 있는 그대로 충실히 파싱한 결과입니다. 수용 검증 기준(중간고사 등 핵심 일정 회수 및 근거 원문 일치)은 완벽히 만족하나, 동일 학사일정이 월별로 중복 표기된 항목(예: 수업평가 설문, 유예 신청 등)은 향후 후속 개선 단계에서 기간 병합(Deduplication) 로직을 적용하는 것을 권장합니다.
2. **다중 주체(학생 vs 행정부서/교수) 일정의 UI 태깅:**
   - 편입생 학점인정 공지의 표에는 학생 신청 기간 외에 학과 심의 기간, 교무처 승인 기간이 함께 포함되어 있습니다. 백엔드 파서는 표의 행 블록을 온전히 회수하였으나, 향후 사용자 경험 개선을 위해 '학생 대상'과 '행정 처리' 일정을 시각적으로 분류하는 메타데이터 태깅을 고려할 수 있습니다.
3. **사전 수용 검사와 실사용자 검증의 범위 분리:**
   - 본 5/5 수용 검증은 로컬에 동결된 실제 한성대 공지 원문 데이터를 대상으로 한 **오프라인 결정론적 파서 사전 검사**입니다. 5/5 달성은 목표 공지의 최소 회수 기준과 결함 방지 계약을 입증한 것이며, 모든 공지 텍스트의 100% 완전성을 보증하는 것은 아닙니다. 실제 재학생 대상 사용성 테스트(UT) 및 운영 환경 배포 검증은 별도 과제로 진행되어야 합니다.

## 5. 결론

N1(시작 시각 오류 대칭 유보), N2(기간-단일 공존 및 TOPCIT 4단계 회수), N3(출처 카드 제목 계약 연결 및 충돌 검출) 세 가지 핵심 결함이 완전히 해결되었으며, Chromium 브라우저 E2E 테스트 및 156개 회귀 테스트를 통해 안정성이 입증되었습니다.
외부 LLM 의존 없이 오프라인 규칙/문맥 기반 파서로서 Zero-Auto-Save 계약과 데이터 무결성(940개 파일 불변)을 완벽히 준수하고 있습니다.
