# CampusRAG 최신 코드·명칭 적용 및 중간발표 인계 프롬프트

아래 내용을 홈서버의 CampusRAG 프로젝트를 연 Codex에 전달한다.

---

CampusRAG 중간발표를 개편하려고 한다. 먼저 GitHub에서 최신 코드와 기존 PPT·대본을 받아 프로젝트 명칭을 운영 서비스에 적용하고, 이 홈서버의 실제 환경을 조사해 발표에 사용할 사실을 확정해줘. 이번 단계에서는 개선된 PPT와 대본을 만들지 말고, 적용 결과·조사 보고서·발표 구성안까지 작성한 뒤 내 결정을 기다려줘.

## 프로젝트와 현재 작업 상황

- 프로젝트명: **CampusRAG**, 팀명: **저학년의 반란**.
- 한성대학교 공개 공지·학사 안내·FAQ·서식을 검색해 근거 기반 답변과 공식 원문 링크를 제공하는 챗봇이다.
- 시연 주소: **https://hschatbot.jwlee.dev**.
- 기준 저장소는 `https://github.com/jwlee1008/HSChatBot.git`이다. 다른 개발 PC에는 `origin=pregeon/HSChatBot`, `myrepo=jwlee1008/HSChatBot`으로 등록돼 있으므로 원격 이름만 보고 기준 저장소를 판단하지 마.
- 다른 개발 PC에서는 2026-10-21 기준 원격 `main`을 pull한 뒤 CampusRAG 명칭 변경, 기존 발표자료와 대본, 이 인계 프롬프트를 기준 저장소의 `main`에 반영한다. 서버에서는 실제 원격 커밋과 아래 파일을 확인해서 수신 여부를 검증해줘. Git에 없는 다른 PC의 로컬 지식 DB·미커밋 기능 변경까지 전달됐다고 가정하지 마.
- 다른 PC의 로컬 소스에서 PWA 관련 파일은 확인되지 않았지만, 팀원 한 명이 별도로 PWA 작업을 했다. 서버·다른 브랜치·작업 폴더에 있는 구현을 확인하고 보존해줘.
- 2026-10-21 외부 브라우저 관찰에서는 첫 화면이 아직 CampusMate이고, `/health` 응답은 `llm_provider=local`, `doc_count=7202`였다. 이는 당시 상태 API 관찰값이다. 여기서 현재 값을 다시 확인하고, 실제 모델명·생성 성공·응답 품질을 이 값만으로 단정하지 마.

## 0. 최신 코드·발표자료 받기와 명칭 적용

1. 실제 서비스 저장소, 원격 URL, 현재 브랜치와 미커밋 변경을 먼저 확인해줘. `jwlee1008/HSChatBot`의 `main`이 기준이다. 원격 별칭은 서버 설정에 맞게 판단해줘.
2. 운영 설정·PWA·서버 전용 수정·DB 경로를 보존하고, 변경이 있으면 복구 가능한 별도 Git 브랜치나 백업으로 확보해줘. `.env`와 비밀값은 커밋하거나 출력하지 마.
3. 기준 원격을 fetch한 뒤, 정상적으로 fast-forward 가능한 작업 브랜치에서는 `git pull --ff-only <기준원격> main`으로 최신 코드를 받아줘. 서버 전용 커밋이나 미커밋 변경으로 막히면 충돌을 검토해 통합해줘. reset/clean/강제 덮어쓰기로 해결하지 마. PWA가 원격에 없어도 서버의 기존 구현을 제거하지 마.
4. 아래 파일이 실제로 내려왔는지 확인해줘. **이 파일들은 12장·약 10분 구성의 기존 발표본이고, 앞으로 만들 8장·시연 포함 개편본은 아니다.** 기존 내용을 읽고 개편 기준으로 활용해줘.
   - `outputs/campusrag_midterm_20261019/CampusRAG_중간발표_10분_v1.2_20261019.pptx`
   - `outputs/campusrag_midterm_20261019/CampusRAG_중간발표_대본_20261019.docx`
   - `outputs/campusrag_midterm_20261019/CampusRAG_중간발표_대본_20261019.md`
   - `outputs/campusrag_midterm_20261019/README.md`
   - `docs/campusrag_home_server_presentation_handoff_20261021.md`
   - 관련 PRD·설계 자료는 `docs/README.md`, `docs/chatbot_release_20261007/`, `outputs/campusrag_design_20261018/`에서 찾아줘.
5. 운영 서비스의 화면 제목·첫 안내·프로젝트 정보·PWA 이름 등 사용자에게 보이는 명칭을 CampusRAG로 맞춰줘. 이 **명칭 변경을 적용하는 데 필요한 웹 빌드와 해당 서비스의 재시작·재배포는 진행해줘.** 현재 홈서버의 실행 방식과 설정을 유지하고, 문제가 생기면 이전 성공 버전으로 복구해줘.
6. 기존 PWA의 manifest·service worker·설치 이름과 캐시 갱신도 확인해줘. 이미 설치한 앱에서 이전 이름이 남는 경우 반영 범위와 재설치 필요 여부를 보고해줘.
7. 모델·임베딩·운영 DB·활성 자료 버전은 명칭 변경 때문에 교체하지 마. 이번 Git 반영에 대용량 Chroma DB는 포함되지 않으며, 기존 Docker 영속 볼륨도 이미지 재빌드만으로 교체하지 마.
8. 적용 후 실제 도메인에서 CampusRAG 표기, 질문·답변·원문 링크, 기존 PWA 동작을 확인하고 적용 커밋과 결과를 기록해줘.

## 1. 실제 서버와 운영 코드 확인

1. OS, CPU, RAM, GPU와 VRAM, 실제 실행 프로세스와 서버 저장소 경로를 확인해줘.
2. Docker/Compose, systemd, 직접 실행 등 실행 방식을 찾아 실제 서비스가 쓰는 코드 경로·브랜치·커밋·이미지·마운트·실행 명령을 확인해줘. 저장소 HEAD와 실행 중인 서비스 버전은 구분해줘.
3. 최신 코드 수신과 명칭 적용 전후의 서버 수정·미커밋 변경을 비교해줘. 보존한 서버 전용 기능과 실제 반영 커밋을 기록하고, 저장소 버전과 실행 중인 프로세스·이미지 버전이 같은지 확인해줘.
4. `.env`, API 키, 비밀번호, 토큰과 원본 전체 환경변수는 출력하거나 보고서에 넣지 마. 필요한 비밀이 아닌 모델·제공자·데이터 경로만 확인해줘.
5. 실제 LLM 제공자와 모델명, 추론 실행 방식(Ollama, Transformers 등), CPU/GPU 사용 여부를 확인해줘. 질문 임베딩 모델과 답변 생성 모델을 구별해줘. 코드 기본값보다 실제 프로세스 설정·모델 서버·실행 로그를 우선해서 판단해줘.

## 2. 모델과 배포 구조의 변경 이력

발표에서는 다음 변화 과정을 설명하고 싶다.

**초기 경량 오픈소스 모델·무료 호스팅 시도 → Gemini API 사용 → 현재 홈서버 운영**

- Git 이력, 배포 파일, 문서와 로그에서 각 단계의 모델·플랫폼·변경 사유를 확인해줘.
- 초기 코드 기본값에 `Qwen/Qwen2.5-1.5B-Instruct`가 있고 일부 과거 설명에는 Gemma가 등장한다. 실제 사용한 모델과 단순 기본값·계획을 구별해줘.
- 무료 호스팅이 Cloudtype이었는지, 다른 플랫폼도 실제 사용했는지 확인해줘.
- 메모리 제한, 초기 로딩, 속도, 답변 품질, 호출 한도·비용 중 실제 변경 사유로 뒷받침되는 내용을 정리해줘. 근거가 없으면 추측으로 채우지 마.
- 현재 홈서버가 웹·검색만 맡고 외부 API가 생성하는지, 생성까지 홈서버에서 수행하는지 분명히 밝혀줘.
- 이력이 불확실하면 발표에서는 모델명을 생략하고 ‘경량 오픈소스 모델’로 표현하는 안을 제안해줘.

## 3. 운영 기능과 시연 가능 여부 확인

- 실제 배포 화면, `/health`, 검색과 질의 API, 공식 원문 링크를 확인해줘.
- 대표 질문 2~3개로 실제 답변·근거·응답시간을 확인해줘. 가능하면 학사 안내 1개와 공지 질문 1개를 선정해줘. 없는 신청 기간이나 사실을 예시 정답으로 만들지 마.
- 첫 요청과 반복 요청의 시간을 구별하고, 답변과 원문이 일치하는지 확인해줘. 이 소수 사례를 전체 정확도로 환산하지 마.
- 현재 운영 데이터 규모, 최근 수집일·적용일, 활성 검색 DB와 통합 JSON, 자동 갱신 작업의 설치·최근 실행 결과를 확인해줘. `doc_count`가 청크 수인지 원문 문서 수인지 코드로 확인해줘.
- PWA의 manifest, 아이콘, service worker, HTTPS, 설치·독립 창 실행 상태를 확인해줘. 구현 존재와 실제 단말 설치 검증은 구분해줘. 설치가 된다고 오프라인에서도 AI 답변이 가능하다고 설명하지 마.
- PC 웹 시연과 PWA 실행 중 실제로 확인된 범위를 바탕으로 **3분짜리 시연 순서**를 추천해줘. 응답 대기와 화면 전환 시간도 포함하고, 장애 시 보여줄 실제 답변 캡처·녹화 준비 방법도 제안해줘.
- 명칭 적용 후에도 화면이나 설치한 PWA에 예전 이름이 남는지 확인하고, 캐시·미반영 빌드 등 원인과 처리 결과를 기록해줘.

## 4. 확정된 발표 조건

- **총 10분: 설명 7분 + 실제 서비스 시연 3분.** 질의응답은 별도.
- 발표·코드·서비스의 공식 명칭은 **CampusRAG**.
- 팀원은 네 명이고 **이름 칸은 전부 비워둔다**. 이름을 다시 질문하지 마.
- 역할분담안:
  1. 개발 총괄: 전체 설계, 핵심 개발, 통합·배포. 4학년인 내가 담당.
  2. PWA 구현: 설치·앱 실행 기능.
  3. 데이터 수집: 공식 자료 수집·정리.
  4. 기능 테스트·사용성 점검: 예시 질문 작성, 답변과 원문 대조, 모바일 확인, 오류 정리.
- 네 번째 역할의 수행 이력은 아직 확정되지 않았다. 이미 완료한 기여로 만들어 쓰지 말고, 실제 수행 여부 또는 향후 담당으로 구분해줘. 학년이나 개인별 역량을 평가하는 표현은 넣지 마.

## 5. 발표 내용 개편 방향

기존 발표는 12장이며 아래처럼 수정하려고 한다.

- 기존 2번의 문제 제기는 간단한 프로젝트 소개로 대체.
- 기존 3번은 현재 구현 기능 설명으로 개편.
- 기존 4번 사용자 화면 슬라이드는 삭제하고 실제 사이트에서 시연.
- 기존 5번은 모델·배포 변화 과정과 현재 시스템 구조를 설명. 필요하면 두 장으로 분리.
- 기존 6번 데이터 규모, 7번 예외 처리, 8번 검증 수치는 본문에서 빼고 대본 맨 끝 질문 대비로 이동.
- 기존 9번에서 설계 산출물 소개는 빼고 개발 완료 항목과 앞으로 개선할 부분을 정리.
- 기존 10·11·12번의 문제·평가·계획은 위 개발 현황에 통합.
- 역할분담 슬라이드 추가.

현재 제안한 구성은 **표지 / 프로젝트 소개 / 구현 기능 / 개발 과정의 변화 / 현재 시스템 구조 / 실제 시연 / 개발 완료·개선할 일 / 역할분담**, 총 8장이다. 실제 확인 결과와 7분 설명 시간에 맞춰 검토해줘.

대본 끝의 예상 질문에는 RAG를 쓰는 이유, 데이터 범위와 최신성, 모델·서버 변경 이유, 비용·속도, 답변 오류, 검증 결과, PWA 설치·오프라인 범위를 포함할 예정이다. 실측값과 목표값, 로컬 기록과 운영 상태는 구분해줘.

## 6. 이번 단계 결과물

`docs/campusrag_home_server_presentation_audit_YYYYMMDD.md`로 보고서를 저장해줘. 날짜는 실제 작업일로 넣어줘. 보고서는 다음 순서로 정리해줘.

1. Git pull·명칭 적용 결과, 기존 PPT·대본 수신 여부와 현재 운영 구조 한 문장.
2. 하드웨어, 실제 모델·추론 방식, 운영 코드 버전, 데이터·자동 갱신, PWA 확인 결과 표.
3. 초기 모델·무료 호스팅부터 현재 홈서버까지의 변화 과정과 근거·미확정 사항.
4. 발표에 넣을 개발 완료 항목과 실제로 남은 개선 과제 2~3개.
5. 3분 시연에 사용할 실제 질문, 기대 출처와 관찰한 응답시간, PWA 포함 가능 여부.
6. 8장 구성안과 설명 7분·시연 3분 배분.
7. 발표 확정에 꼭 필요한 미결정 사항만 질문.

운영 서비스·기존 PWA·DB·모델·설정을 보존해줘. 최신 코드 수신과 명칭 적용을 위한 빌드·재시작은 수행하되, 모델 교체, 전체 재수집·재색인, 새로운 PWA 기능 개발이나 개선된 PPT·대본 제작은 이번 범위에서 제외해줘. 조사 결과를 확인한 뒤 내가 발표 개편 등 다음 작업을 결정하겠다.
