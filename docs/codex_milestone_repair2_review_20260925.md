## A — P1: 공통 날짜·시간 검증이 모든 반환 경로에 적용되지 않음

위치: `backend/schedules/extraction.py:112` 취소, `:301` 조건부 선착순, `:340` 반복 기간, `:1019` 시간 포함 기간, `:1068` 날짜 기간, `:1112` 휴업일 등의 분기.

직접 함수 실행 시 기준 시각은 `2026-09-25T12:00:00+09:00`으로 고정했다.

| 입력 | 실제 결과 |
| --- | --- |
| 행사 취소 안내: 2027년 2월 30일 25:90 예정되었던 음악회 행사는 취소되었습니다. | `2026-02-30T25:90:00+09:00`, 시각 확정 true, ambiguous false. 명시 연도도 무시 |
| 신청 기간은 2026년 2월 30일 09:00부터 2026년 3월 5일 18:00까지입니다. | 시작 `2026-02-30T09:00:00+09:00`, 시각 확정 true, ambiguous false |
| 교육 기간은 2026년 2월 30일부터 2026년 3월 5일까지입니다. | 시작 `2026-02-30` 유지. 모호 사유는 날짜 오류가 아닌 시험 시간 미정 |
| 2026년 2월 30일은 개교기념일로 전체 휴업일입니다. | 시작/종료 `2026-02-30` 유지. 날짜 오류 유보가 아님 |
| 신청은 2월 30일 25:90 오픈 ~ 3월 5일 18:00 마감이며 선착순 조기 마감됩니다. | 시작 `2026-02-30T25:90:00+09:00` 유지, 시각 확정 true |

`_check_calendar_validity` 호출을 일부 분기에 추가했지만 위 분기들은 검증 없이 후보를 반환한다. `is_ambiguous=True`만으로 잘못된 날짜가 제거되는 것도 아니다. 잘못된 문자열이 날짜 필드에 남으면 UI와 후속 처리에서 신뢰할 수 없다.

요구: 후보 반환을 하나의 검증 경로로 통합하거나, 모든 분기에 검증 적용을 입증할 구조를 만들 것. 실제 날짜/시간, 시작≤종료, 명시 연도 보존을 확인하고 오류값은 확정 필드에 남기지 말 것. 수정한 반례뿐 아니라 각 분기의 정상/비정상/누락 입력을 검증할 것.

## B — P1: 원문에 없는 업무명과 마감 시각을 아직 생성

위치: `backend/schedules/extraction.py:272`–287, `:627`.

1. 입력: `장학금 신청은 11월 1일부터 11월 5일까지이며 마감일에 전산 마감됩니다.`
   - 실제 제목: **제3전공 이수신청**
   - 실제 종료: **2026-11-05T17:30:00+09:00**
   - `is_time_confirmed=True`, `is_ambiguous=False`.
2. 입력: `장학금 신청 마감일이 당초 11월 1일에서 11월 5일로 연장되었습니다.`
   - 실제 종료: **2026-11-05T15:00:00+09:00**
   - 시각은 원문에 없지만 `is_time_confirmed=True`, `unconfirmed_fields=[]`.

원인은 `m_time` 미매칭 시 17:30, 연장 시각 미매칭 시 15:00을 넣는 기본값과 고정 제목이다. `source_quote in text` 통과는 후보의 날짜/시간/제목이 근거에 있다는 뜻이 아니다.

요구: 원문에서 확인되지 않은 시간은 null/미확정으로 유지하고 사용자 입력 전 확정 저장을 막을 것. 업무명은 원문 기반으로 추출하거나 중립적인 이름을 사용할 것. 보고서의 '하드코딩 제거 완료' 표현은 실제 전체 분기 점검 후에만 사용할 것.

## C — P2: 종료 시각만 바꿔도 시작 시각의 초·마이크로초가 유실

위치: `frontend-web/src/App.tsx:127`, `:1057`–1106.

실제 Chromium에서 TIME_CONFIRMED_EVENT를 열어 **종료 시각만 11:00으로 변경**했다.

| 필드 | 수정 전 API 응답 | 수정 후 API 응답 |
| --- | --- | --- |
| 시작 | `2026-11-20T00:00:45.123456Z` | **`2026-11-20T00:00:00Z`** |
| 종료 | `2026-11-20T01:00:55.654321Z` | `2026-11-20T02:00:00Z` |

종료는 의도대로 변경됐지만 시작은 손대지 않았는데 45.123456초가 사라졌다. `isDateOrKindModified`가 날짜/시각 전체를 하나로 묶어 판단하고 모든 시각 필드를 분 단위 UI 값으로 재작성하기 때문이다.

요구: 일정 유형이 같다면 시작과 종료를 독립적으로 변경 추적하고, 미변경 쪽은 PATCH에서 제외하거나 원본 문자열을 그대로 보존할 것. 유형 변경 때 필요한 null 정리는 별도로 처리할 것. 시작만 변경/종료만 변경/제목만 변경의 반대편 정밀도 불변을 검증할 것.
